# Tack k3s Implementation Plan

## Goal and constraints

Move Tack’s application to one Debian 13 VM on Vault, after QA validation. Then switch all existing Tack hostnames to `cloudflared` inside k3s.

Keep this change in configs. Preserve Tack’s Dockerfiles, application code, audit consumer, data services, operator commands, and existing deployment wiring. Cleanup remains separate.

Use the agreed defaults:

- Provision 4 virtual CPUs, 8 GiB RAM, and a 40 GiB disk per VM.
- Run one k3s server with embedded etcd, two application replicas, and later two `cloudflared` connectors.
- Define plain Kubernetes resources through OpenTofu.
- Save compressed etcd snapshots every 12 hours, retaining five locally and remotely. Preserve the server token separately.
- Pin cloud images, k3s downloads, and application images to immutable identities.

Apply this networking requirement:

| Component | Required networking |
|---|---|
| Debian VM | Configure IPv4 and IPv6 addresses. |
| K3s Pod network | Configure IPv6-only Pod address ranges. |
| Kubernetes Services | Configure IPv6-only Service addresses. |
| Tack application | Use ordinary IPv6-only Pods and IPv6 connections to existing data services. |
| `cloudflared` | Share the VM’s network and automatically use available IPv4 or IPv6 Internet connectivity. |

Configure `cloudflared` with `hostNetwork: true`, `dnsPolicy: ClusterFirstWithHostNet`, and `--edge-ip-version auto`. Do not bind its outgoing connection to a particular address family. [Cloudflare address-family selection](https://developers.cloudflare.com/tunnel/reference/run-parameters/), [Kubernetes host-network DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)

The available Internet address family must not change Tack’s internal IPv6 network. Preserve the existing data services’ network configuration.

## Implementation tasks

### Task 1: Provision the QA VM and k3s

Consume the existing Suburban networking, storage, SSH, and Proxmox provider inputs.

- Add the QA VM identity and instantiate the new module from the existing QA root.
- Use cloud-init to establish networking and start the QEMU guest agent before guest-management resources run.
- Reuse shared guest preparation inside the new module. Give each new VM exactly one preparation owner.
- Install pinned k3s through existing download, file, and systemd resources.
- Implement the networking requirements above. Select the node’s IPv6 address for Kubernetes communication.
- Disable bundled Traefik and ServiceLB.
- Configure native etcd snapshots to the existing object store using an isolated QA prefix and protected credentials.

Produce the VM identity, address, and running cluster. Expose neither credentials nor tokens as outputs.

Verify guest-agent access, node readiness, the assigned Pod and Service address families, snapshot creation, and an unchanged repeat OpenTofu plan. Commit and review.

### Task 2: Deploy and validate the QA application

Consume Task 1’s cluster and the existing QA application inputs.

- Deploy the current application image with `serve --execute --operator-service tack-app`.
- Create the internal Service and two replicas. Configure `/healthz` readiness and rolling updates with zero unavailable replicas and one additional replica.
- Deliver required credentials and certificates through protected files.
- Bootstrap the writable FoundationDB client file without overwriting later coordinator updates. Give each replica a separate persistent log directory.
- Add the restricted Kafka listener required by the new VM. Preserve the existing internal listener and broker data.

Use the existing remote QA workload against both application replicas. Verify authentication, writes, search, continued pages across replicas, authorization refusals, and permanent audit evidence. Verify actual IPv6 connections to the existing data services.

Verify one rolling update and one snapshot restoration on the QA VM. Commit and review.

### Task 3: Deploy the validated application on Vault

Consume the accepted QA configuration and current production image digest.

- Instantiate the same module with production networking, credentials, and a separate snapshot prefix.
- Preserve existing database roles, cluster identities, volumes, and consumer offsets.
- Add the production Kafka listener with access restricted to the new VM.
- Leave existing application containers running.

Verify both replicas, ready Service endpoints, actual image identities, authenticated reads, search, and permanent audit evidence. Do not run production data generation or failure injection.

Commit and review.

### Task 4: Switch Tack to the dedicated tunnel

Start this task after application validation.

- Create a dedicated Tack tunnel in the existing Cloudflare root. Preserve the shared tunnel used by other applications.
- Run two one-replica `cloudflared` Deployments with protected token delivery and the host-network configuration above. Assign metrics ports 2000 and 2001 to avoid a port conflict on the shared VM network. Update one connector at a time.
- Configure their origin as `http://tack-app.tack.svc.cluster.local:8000`.
- On QA, verify automatic connection establishment with IPv4-only Internet access and with IPv6-only Internet access. Keep internal IPv6 connectivity available during both checks.
- Verify that the origin resolves to the IPv6 Service address.
- Switch `tack.goodkind.io` first. Verify requests, TLS, and audit evidence before switching the aliases and `tack.home.goodkind.io`.
- Update applicable private DNS overrides. Preserve previous targets for rollback.

Verify every final hostname and confirm unrelated proxy applications still work. Commit and review.

## Completion and rollback

Run configs linting and validation for the changed roots. Require unchanged repeat plans after deployment.

The final review must check credential handling, network address families, application and broker connectivity, snapshot recovery, hostname coverage, and preservation of unrelated services. Record operator identity, deployed image evidence, and QA results with the PR.

If cutover validation fails, restore the previous DNS targets. Keep the old containers, routes, and Compose release wiring until a separate cleanup change.
