# Provision secrets for a Terrakube deployment

Keep the deployment disabled while preparing its credentials. Select the manifest for the target environment. [Tack QA](../../../.github/terrakube/secrets/tack/tack-qa.json) and [Tack production](../../../.github/terrakube/secrets/tack/tack-prod.json) use separate 1Password vaults.

1. Create the vault named by the manifest. Create one 1Password service account for this deployment and grant it read access to that vault only. Store its service account token in the trusted deploy executor under the environment variable identified by `service_account_env`. Keep the executor token out of GitHub Actions, preview jobs, application pods, and OpenTofu input variables. [1Password service accounts](https://developer.1password.com/docs/service-accounts/get-started/)
2. Provision the credentials at each issuer before populating the referenced 1Password fields. Grant the Proxmox principal access to the target deployment's guests and required operations. Restrict the deployment SSH identity to the required hosts, verify their host keys independently, and restrict provider release access to reading the required private releases. Restrict the production SeaweedFS snapshot identity to the deployment's backup objects. Verify that each identity fails an operation outside its assigned scope. Keep deployment disabled if an issuer still grants broader access.
3. Isolate state access. QA and production currently use different keys in the same R2 bucket. A permanent object read/write token for that bucket grants access to other workspaces. With the two AWS credential fields in these manifests, provision a separate state bucket for each deployment and grant its token access to that bucket only. Move the existing state during a separately approved migration. A temporary R2 credential scoped to exact objects would also require a session token and a refresh mechanism. [R2 authentication](https://developers.cloudflare.com/r2/api/tokens/)
4. Preserve state continuity during that migration. Stop writers for the affected workspace and back up its encrypted state. Use its existing passphrase to verify that the backup can be read. Migrate the backend under exclusive access. If rotating a shared passphrase, follow the OpenTofu encryption migration procedure with the old decryption key available until the new key can read the migrated state. Verify the state lineage, serial, resource addresses and lock behavior with the target identity before resuming writes. Keep recovery keys available for encrypted backups. [OpenTofu state encryption](https://opentofu.org/docs/language/state/encryption/)
5. Populate each reference with the assigned environment's value. Keep application roles distinct when migrating existing database passwords, certificates and signing keys. The deploy executor provisions the runtime credentials. The audit writer needs its writer credential. It must not receive operator, migrator or other administrative credentials. Verify the actual process environment and mounted secrets before enabling the deployment.
6. Check the manifest and resolver using synthetic values first. A candidate reference must identify a field in the target vault. Missing fields, an unexpected service account, a reference to another vault, or a job for another deployment must fail before OpenTofu starts. Verify with synthetic markers that logs, saved plans and state do not disclose resolved credentials. Grant production access only after validating the separate QA deployment and its credential restrictions.

For another service, create a manifest in the same layout using its enrollment and deployment names. Use reference URIs for field values and an environment variable name for the service account token. Keep resolved values out of repository files and OpenTofu resources that record their inputs in state. [1Password secret references](https://developer.1password.com/docs/cli/secret-references/)
